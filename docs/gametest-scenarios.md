# GameTest Scenarios — Easy Homes

Proposal for automated end-to-end tests based on the vanilla **GameTest framework**,
run through **ModDevGradle** on the NeoForge nodes of the Stonecutter build.

Status: **approved** — review decisions are recorded in section 5.

## 1. Scope

**In scope (server-side, where the mod logic lives):**
- All six commands: `/sethome`, `/home`, `/delhome`, `/renhome`, `/homes`, `/back`
- Repository behavior: limits, cooldown, persistence on disk
- Cross-dimensional teleports and guard clauses (unknown dimension, out-of-bounds position)
- **All 10 Stonecutter nodes** — NeoForge via ModDevGradle, Fabric via
  `fabric-gametest-api-v1` (decision Q3)

**Out of scope:**
- Client side: keybind, screens, Xaero's Minimap integration (needs a client gametest
  setup — possible follow-up)
- Exact i18n message texts — we assert exit codes and observable state, not strings

## 2. Infrastructure (as implemented)

- Tests live in the shared Stonecutter tree under `src/main/java/.../gametest/`
  (plus the structure template in `src/main/resources/data/easy_homes/structure/`)
  so they get preprocessed per node like the mod itself. They never ship in the
  artifacts: every jar task excludes the `gametest` package and the template.
- Registration differs per era, hidden behind `//? if` guards:
  - **NeoForge 1.21.4**: vanilla `@GameTest` + `@GameTestHolder` +
    `@PrefixGameTestTemplate` + `RegisterGameTestsEvent.register(Class)`.
  - **NeoForge 1.21.5 – 26.1**: registry-based system — `RegisterGameTestsEvent`
    with a `FunctionGameTestInstance` per scenario from the shared
    `Scenarios` catalogue (vanilla 1.21.5 replaced the annotation framework).
  - **Fabric (all versions)**: the `fabric-gametest-api-v1` module (pulled
    transitively by Fabric API) discovers the scenario classes through the
    `fabric-gametest` entrypoints in `fabric.mod.json`. That key is resolved
    lazily, so production jars are unaffected by the excluded classes.
- Run configurations: `./gradlew :<node>:runGameTestServer` on every node.
  NeoForge exits with the number of failed required tests; Fabric writes a
  JUnit XML report (`build/reports/gametest/gametest.xml`) and fails the task
  on test failures.
- CI: `.github/workflows/gametests.yml` runs a per-node matrix on push/PR.

## 3. Test harness conventions (as implemented)

- **Players**: each scenario builds a detached `ServerPlayer` via `Eh.player(...)`
  — constructor + fake `ServerGamePacketListenerImpl` with a black-hole
  `Connection` whose `send` is a no-op. On NeoForge the connection also gets a
  sink `EmbeddedChannel` and the mod's payload channels registered as ad-hoc,
  because NeoForge reads connection state from netty channel attributes.
  Players are never added to the world, do not tick, and carry a fresh UUID, so
  tests never share repository state.
- **Method shape**: `public void x(GameTestHelper)` instance methods; on the
  1.21.4 nodes a Stonecutter guard turns them `static` (vanilla 1.21.4
  reflection requires static, fabric-gametest-api 3.x+ forbids it).
- **Commands**: executed through the live brigadier dispatcher
  (`getDispatcher().execute(command, player.createCommandSourceStack())`);
  the returned exit code is the primary assertion.
- **Config overrides**: tests mutate the MidnightConfig statics directly and
  reset repository state per player (`Eh.reset`).
- **Impossible states** (unknown dimension, out-of-bounds coordinates) are
  seeded through `HomeRepository` directly.
- **Cooldown timing**: the game test server accelerates ticks far beyond
  wall-clock time, so HOM-5 asserts the blocked phase in real time and then
  rewinds `lastTeleportation` to simulate the second having passed —
  deterministic on any machine speed.
- **Structure**: `easy_homes:platform` — a 7×5×7 stone floor (generated by
  `tools/GenPlatform.java`), giving fake players ground to stand on.

## 4. Scenarios

Priority: **P1** = happy paths and core limits, **P2** = guard clauses and edge
cases, **P3** = tricky/low-value, included for completeness.

### 4.1 `/sethome`

| ID   | Pri | Scenario | Expected |
|------|-----|----------|----------|
| SET-1 | P1 | Survival player runs `/sethome` (no args) | Exit 1; repository contains home `main` at the player's position |
| SET-2 | P1 | `/sethome base` | Exit 1; home `base` stored with position and rotation |
| SET-3 | P1 | `/sethome base` again after moving | Exit 1; coordinates updated (overwrite allowed) |
| SET-4 | P2 | `/sethome foo bar` (space), 65-char name, cyrillic name | Exit 0; nothing stored |
| SET-5 | P2 | `/sethome -` | Exit 1; auto-generated name `<dimension>_<x>_<y>_<z>` stored |
| SET-6 | P1 | `maxHomes = 2`; survival player creates 2 homes, attempts a 3rd | 3rd `/sethome` exits 0 and is not stored |
| SET-7 | P2 | Same, but creative player | All homes created, limit ignored |
| SET-8 | P1 | After SET-2, simulate relogin: `forgetConfig` → `loadConfig` | `<world>/data/easy_homes/<uuid>.json` exists on disk; home still resolves after reload |

Overwrite is allowed even at the homes limit (SET-3 + SET-6 combined: replacing an
existing name while at `maxHomes` succeeds) — current behavior, covered by SET-3.

### 4.2 `/home`

| ID   | Pri | Scenario | Expected |
|------|-----|----------|----------|
| HOM-1 | P1 | `/home base` after moving away | Exit 1; player at stored coords in stored dimension, rotation preserved |
| HOM-2 | P1 | `/home` (no args) | Teleports to default home `main` |
| HOM-3 | P1 | `/home unknown` | Exit 0; player did not move |
| HOM-4 | P2 | `/home "foo bar"` (invalid name) | Exit 0; no teleport |
| HOM-5 | P1 | `cooldown = 1`, survival: teleport, immediately teleport again, then wait ~30 ticks and retry | 2nd attempt exits 0; attempt after the wait succeeds |
| HOM-6 | P2 | Same as HOM-5 with creative player | Both teleports succeed immediately |
| HOM-7 | P1 | Player walks in the nether, sets a home, returns to overworld, `/home <nether home>` | Player ends up in the nether at the stored coords |
| HOM-8 | P2 | Repository-seeded home with dimension `easy_homes:does_not_exist` | Exit 0; unknown-level error; player stays |
| HOM-9 | P2 | Repository-seeded home with y far outside build limits | Exit 0; invalid-position error; player stays |
| HOM-10 | P3 | Player riding a boat it controls | Exit 0; mounted error; not teleported |

## 5. Review decisions

1. **REN-4 — rename onto an existing name** silently overwrites the target home.
   *Decision: this is expected behavior* — locked in with a test as-is.
2. **`PacketSender` vs mock player** — informational note, no decision needed:
   `player.connection.send(...)` goes to the fake connection of a mock player and
   is expected to be a harmless no-op. If it ever throws, we guard it; SMK-1
   verifies this on day one.
3. **CI matrix** — *Decision: all 10 nodes, NeoForge and Fabric alike.*
4. **Cooldown waits** — *Decision: accepted.* E2E tests should verify real behavior,
   1-second wall-clock waits included.

## 6. Implementation status

Complete — all scenarios implemented and green on all 10 nodes
(1.21.4 nodes run 31 tests; 1.21.5+ nodes run 32 including the framework's
builtin `always_pass`). CI runs the full matrix on every push and PR via
`.github/workflows/gametests.yml`. The structure template can be regenerated
with `java tools/GenPlatform.java gen <out.nbt> 7 5 7`.
